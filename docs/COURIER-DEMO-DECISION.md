# Courier demo provider decision

Use the local deterministic mock provider for this implementation; do not connect ShipAny or another external courier service. The endorsed scope requires a demo-only flow with no real shipment, payment, or live credentials. It permits ShipAny sandbox only if free access and access for this project are confirmed; otherwise it calls for the local mock fallback.

ShipAny’s [developer docs](https://shipany.in/developers) say sandbox keys return simulated couriers, simulated AWBs, and labels with zero live courier calls and zero wallet movement, but the quick start lists “Get API Access” before creating a sandbox key. The public [pricing page](https://shipany.in/pricing) describes no subscription/minimum volume for its shipping service and a prepaid wallet for live bookings; it does not establish whether this project’s API/sandbox onboarding is available without a separate access or setup cost. ShipAny’s [Terms & Conditions](https://shipany.in/terms), section 2, also require users to be legally capable of entering a binding contract to use the service for business purposes.

No provider account was created, no credentials were entered, and ShipAny was not contacted. Since project-specific sandbox access and eligibility were not confirmed—and the task prohibits contact or credential entry—the in-scope choice is the local mock. It emits synthetic INR rate options and demo tracking data but makes no external courier call, creates no real booking or label, moves no parcel, and processes no payment. A real-provider integration would require separate owner authorization and verified access/eligibility.
