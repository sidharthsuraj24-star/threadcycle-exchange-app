# Requirement audit against both supplied briefs

**Status labels:** **Pass** means the requirement is implemented in the inspected source and/or exercised by the listed tests; **Partial** means a narrower version exists or some part is unverified; **Missing** means no implementation was found; **Not testable** means the requirement needs a live service, external capability, real-world event, or evidence unavailable during this code-only audit. The line-addressable duplicate brief is `pasted_content_2.txt`; the first full brief is `pasted_content.txt`. Evidence paths below are relative to the repository root.

## User, listing, browsing, and swap requirements — spec references: `pasted_content_2.txt` lines 33–65 and 155–160

| Requirement | Status | Evidence |
|---|---|---|
| User registration and login | **Pass** | `server/app.js:141-180` validates email/password, hashes with bcrypt, rotates the session, and authenticates; integration coverage includes registration, login, duplicate/failed-login and hashed-password checks (`tests/marketplace.test.js:63-85`). |
| Personal profile creation and editing | **Pass** | Registration collects name/email/city (`server/app.js:141-152`); authenticated profile GET/PATCH and dashboard profile form are in `server/app.js:336-345` and `public/app.js:149-160`. Profile update is integration-tested (`tests/marketplace.test.js:87-94`). |
| Listing creation and clothing details (type/category, size, brand, condition, description) | **Pass** | Validation and persistence are in `server/app.js:119-125,217-224`; listing fields are modeled in `server/models.js:23-42`. |
| Listing images, item detail, and availability status | **Pass** | JPEG/PNG/WebP signature-checked uploads, up to four images, and byte storage in MongoDB are implemented in `server/app.js:104-117,207-235` and `server/models.js:17-42`; detail and status UI are in `public/app.js:103-107,156`. Tests cover upload, persistence, type validation, and detail/photo response (`tests/marketplace.test.js:96-119`). Images are optional in the form, so the system does not enforce a minimum photo count. |
| Edit or remove own listings | **Pass** | Owner and availability checks guard edit/removal (`server/app.js:225-245`); dashboard controls are in `public/app.js:149-160`. Tests create, edit, remove, and verify photo removal (`tests/marketplace.test.js:96-119`). |
| Browse/filter by category and location (also text/size) | **Pass** | Client filters are in `public/app.js:82-90`; API applies category, size, city, and text filters and caps page results (`server/app.js:187-199`). City is an exact broad city-name filter, not geospatial search. API city filtering is exercised in `tests/marketplace.test.js:121-130`. |
| Send requests, review incoming requests, accept/reject, withdraw, and track current state | **Pass** | Swap creation validates two available member-owned listings and recipient identity (`server/app.js:263-275`); current request records populate dashboards (`server/app.js:277-282,346-355`); recipient accept/decline, requester withdrawal, and state transitions are implemented at `server/app.js:284-317`. Tests exercise request, withdrawal, decline, acceptance, reservation, and completion (`tests/marketplace.test.js:132-160,185-200`). |
| Manage swap history, including prior state transitions | **Partial** | Dashboard and swap API list current records/status/timestamps (`server/app.js:277-282,346-355`), but the model stores only the current `status`, `createdAt`, and `updatedAt` (`server/models.js:45-57`); there is no immutable transition/event history. |
| Negotiation chat between the two participants | **Pass** | Request-linked messages persist; access checks require participation (`server/app.js:318-334`, `server/models.js:60-66`). The integration suite verifies both participants can read/write and an outsider receives 404 (`tests/marketplace.test.js:132-148`). |
| Confirm the swap agreement after negotiation | **Partial** | A requester proposes a pair and the recipient can accept or decline (`server/app.js:263-275,284-298`), and both can later confirm completion (`server/app.js:302-308`; UI `public/app.js:131-147`). There is no separate, jointly recorded “terms agreed” step after chat; the two-person confirmation is specifically treated as completion, not agreement before exchange. |
| Swap estimate based on category, condition, and brand | **Partial** | Server formula uses category guide × condition factor × **brand tier**, rounded to ₹50 (`server/value.js:1-24`, `server/app.js:119-125,182-185`). The typed brand label itself is not used in the formula or linked to a brand catalog, so this is tier-based guidance rather than exact-brand estimation. |
| Display an item-to-item value comparison and suggest fair matches | **Pass** | Swap cards and chat display both estimates and their gap (`public/app.js:124-147,183-191`); `/api/matches` sorts by city and relative estimate gap and returns a score (`server/app.js:248-260`). The UI warns that estimates are not prices or fairness guarantees (`public/app.js:96,106,190`). |
| Show nearby members and nearby swap opportunities | **Partial** | Matching uses explicitly entered city text and value comparison, excludes demo listings, and boosts same-city matches (`server/app.js:248-260`). It is not distance/radius matching, and the match endpoint does not filter out listings from other cities; “nearby” therefore means a coarse same-city preference, not geographic proximity. No GPS is intentionally collected (`docs/PRD.md:30`). |
| Courier integration for remote swaps | **Partial** | Request accepts only `local`, `remote`, or `flexible`; the UI explicitly calls remote/shipping a preference and says no courier is arranged or tracked (`server/models.js:45-57`, `public/app.js:162-175,183-191`). **There is no courier provider/API, booking, rate/label creation, shipment identifier, tracking update/status, exception/cancellation flow, or delivery integration.** Adding a provider and its authorized credentials/consent, shipment lifecycle, privacy controls, and integration tests remains necessary. Manual preference text is not courier integration. |

## Admin, analytics, data, and non-functional requirements — spec references: `pasted_content_2.txt` lines 66–125

| Requirement | Status | Evidence |
|---|---|---|
| Admin manages members, listings, swap activity, and disputes | **Partial** | Role-gated admin data/actions are implemented: suspend/restore members, hide/restore listings, inspect swaps, and close disputes (`server/app.js:357-400`; UI `public/app.js:194-203`). First-admin promotion requires a trusted owner CLI command, an existing non-demo account, and exact-email confirmation (`scripts/promote-admin.js:6-23`). The UI/API return only the newest 30 records in each collection and do not provide search/pagination (`server/app.js:362-365`), so older records are not reachable through the panel. Tests cover representative moderation and dispute flows (`tests/marketplace.test.js:162-200`). |

| KPI: number of successful swaps | **Partial** | It counts swaps with two member confirmations, but that is an in-app claim and does not verify a physical exchange or delivery (`server/app.js:302-308,359-367`; `docs/PRD.md:35,47`). |
| KPI: user engagement rate | **Missing** | No event instrumentation, engagement denominator, or time window is stored or calculated (`server/models.js:4-72`, `server/app.js:357-368`). |
| KPI: swap-request conversion rate | **Missing** | There is no conversion calculation or defined request-to-completion denominator; the dashboard only shows raw request and status counts (`server/app.js:357-368`). |
| KPI: active users | **Missing** | The dashboard shows registered member totals, not members active within a defined period; no last-active/event data is recorded (`server/models.js:4-15`, `server/app.js:357-368`). |
| Secure authentication | **Pass** | Password minimum/maximum validation and bcrypt hashing, rate-limited sign-in, server-side sessions, session regeneration, HTTP-only/SameSite Strict cookies, production Secure cookies, CSRF plus same-origin validation, and role checks appear in `server/app.js:29-47,72-96,141-180`. Tests cover representative password, session, CSRF, origin, and authorization controls (`tests/marketplace.test.js:63-94,132-160`). |
| Input validation and safe rendering | **Pass** | Field lengths/enums, bounded request bodies, upload limits and image-signature checks are in `server/app.js:26-27,54-62,104-125,217-236`. The new regression test dynamically renders a malicious member name and confirms it is escaped (`tests/marketplace.test.js:213-240`). |

| Fast search/listing performance | **Partial** | Search is server-side, page size is limited to 24, and category/size/city/status/time indexes are declared (`server/app.js:187-199`, `server/models.js:43`). Email remains private in public views. Demo profiles are synthetic and non-contactable (`server/seed.js:14-28`). |
| User-provided item accuracy, clothing quality, and fair exchange | **Not testable** | Listing validation checks field formats, not whether a garment exists or a condition/brand claim is accurate. | Courier assumption that providers support clothing swaps; effect of shipping costs | **Not testable** | No provider is selected or connected, no service capability was tested, and there is no shipping-cost input or calculation (`public/app.js:162-175`, `server/app.js:263-275`). |
